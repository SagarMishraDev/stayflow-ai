# Analytics Demo Fill (live demo site)

## What it does

The live demo's seeded hotel ("StayFlow Grand Hotel") ships with only a
handful of showcase bookings, which leaves the Analytics graphs nearly
empty. The **demo fill** adds ONE synthetic batch of ~180 realistic
bookings — with guests and payments — to that hotel, spread over the
last ~24 months plus ~30 days ahead, so every Analytics chart,
aggregation, filter and comparison shows a meaningful shape.

The batch is generated by `backend/app/demo_fill.py` and runs **only**
when the environment variable `ANALYTICS_DEMO_FILL` is set, during the
demo wrapper's boot sequence (`app.demo_main` → `app.demo_bootstrap`).
It never runs in the normal application entrypoint, and a failure in
the fill can never stop the service from booting.

## ⚠️ These are synthetic demo records

Every filled row is fake and visibly marked (see below). The batch is
shown on the **live public demo** — anyone viewing the demo Analytics
sees these numbers. Fill only because the demo is a showcase; never
enable this on a database that holds a real hotel's records.

## How the batch is marked (and found again)

Batch tag: `DEMO-FILL-2026`.

- **Guests** — created only by the fill; emails
  `demofill.guestNNN@demo.example`, names prefixed `Demo Guest`.
- **Bookings** — belong to batch guests (the Booking model has no
  reference/notes column, so the guest link is the marker; booking
  sources stay realistic: direct / website / walk_in / agent_chat /
  unknown).
- **Payments** — `reference` values prefixed `DEMO-FILL-`, on top of
  belonging to batch bookings.

Statuses follow the stay dates (past → mostly CHECKED_OUT, ~8%
CANCELLED, spanning today → CHECKED_IN/CONFIRMED, future →
CONFIRMED/PENDING); payments mirror the real shapes used elsewhere in
the project (captured in full, pending, partial advance + pending
remainder, and refunds on a slice of paid bookings/cancellations).

## Render steps — fill

1. Open the `stayflow-ai-demo` service in the Render dashboard →
   **Environment**.
2. Add environment variable: `ANALYTICS_DEMO_FILL` = `1`.
   (It is declared `sync: false` in `render.yaml`, so blueprint syncs
   never overwrite the value.)
3. Save — the service restarts. On boot it migrates/seeds as usual,
   then fills the demo hotel. The boot log shows one line:
   `ANALYTICS_DEMO_FILL: fill done (...)`.
4. Open the dashboard → **Analytics**: the graphs now cover ~24 months.
   Re-booting with the variable still `1` is harmless — the fill is
   idempotent and reports `already_filled` instead of duplicating.

## Render steps — remove the batch

1. In the same Environment screen, change `ANALYTICS_DEMO_FILL` to
   `cleanup` and save (service restarts).
2. On boot, exactly the batch rows are deleted — payments of batch
   bookings → batch bookings → batch guests — and the log shows
   `ANALYTICS_DEMO_FILL: cleanup done (...)`. The hotel's original
   showcase bookings and all other data are untouched.
3. **Delete the `ANALYTICS_DEMO_FILL` variable** once cleanup has run.

## Local use

The same hook fires for a local demo run through the wrapper:

```bash
cd backend
DEMO_SEED=1 ANALYTICS_DEMO_FILL=1 DATABASE_URL=sqlite:////tmp/demo.db \
LLM_PROVIDER=mock EMBEDDING_PROVIDER=hashed \
    uvicorn app.demo_main:app --port 9000
```

Programmatic use (tests, scripts): `app.demo_fill.fill_demo_bookings(db,
hotel, count=180, rng_seed=7)` and `app.demo_fill.purge_demo_bookings(db,
hotel)` — both hotel-scoped and committed as one batch.

For a large dataset in a **separate** database instead (500+ bookings
in its own demo hotel, never the live one), see
`docs/ANALYTICS_DEMO_DATA.md` (`scripts/seed_analytics_demo.py`).
